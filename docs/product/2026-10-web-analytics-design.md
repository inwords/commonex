# Аналитика web: источники и продуктовые воронки

Дата: 22.10.2026. Статус: реализовано в ветке `feat/web-analytics`; production-сбор данных выключен до настройки и проверки счётчика.

Основание: [growth roadmap](2026-09-trip-growth-roadmap.md), прежде всего инициатива «Продуктовая воронка». [Исследование провайдеров](../research/2026-10-web-analytics-provider-research.md).

## Цель и выбор

Подключить Яндекс Метрику для web: видеть источники посещений и конверсию текущих пользовательских действий. AppMetrica оставить на mobile. Единые имена бизнес-событий позволят позднее сопоставлять отчёты, но два сервиса автоматически не образуют общую web/mobile воронку.

Рассмотрены три варианта: AppMetrica на web ради одного поставщика; Метрика на web с существующей AppMetrica на mobile; собственный сборщик и хранилище событий. Рекомендуется второй: он соответствует браузерной аналитике и не требует строить инфраструктуру для первого baseline. Первый не выбираем без документированного браузерного SDK; третий оставляем для групповых метрик.

Метрика документирует [SPA-интеграцию](https://yandex.com/support/metrica/en/code/counter-spa-setup) и [воронки из JS-целей](https://yandex.com/support/metrica/en/reports/funnels). Это покрывает измерение браузерного пути, а не всех требований roadmap.

## Проверенные особенности репозитория

- Android: `initializeAppMetrica.kt` включает отправку только для production, отключает location/app-open/revenue tracking. `AnalyticsBridge` предоставляет только настройку; бизнес-событий в модуле нет.
- Web: Next.js 16 static export + React 19 + BrowserRouter внутри `web/src/app/page.tsx`. Наблюдать маршруты следует внутри этого роутера, не через Next navigation.
- `EventPage.tsx` получает `?token=...`; динамический `/event/:id` также содержит идентификатор поездки.
- `EventService` и `ExpenseService` повторяют запросы через async-retry. Успех и окончательную ошибку измерять снаружи retry, иначе получится завышенная конверсия/число ошибок.
- Выбор текущего участника происходит в `SelectUserList`, плательщик расхода — другая роль. Выбор имени не доказывает реальную личность человека.
- Web собирается в Docker, а CI использует общую матрицу backend/frontend. Переменная контейнера после сборки не меняет статический JS.
- RU/EN privacy policy сейчас описывают AppMetrica как mobile analytics и обещают обновление до расширения аналитики.

## Границы первого выпуска

Включены: источник входа, безопасные просмотры, события создания/приглашения/входа/выбора участника/траты/просмотра долгов/возврата, клик в магазин, настройки необязательной аналитики, документация отчётов.

Не включены: правки Android/backend, cross-device identity, app-install attribution, вычисление CAT, 90-дневного повторного создания поездки и группового referral. Не имитировать ещё отсутствующие trip closed, correction/void и offline synced. Web после успешного API-сохранения отправляет `expense_submitted`, а не мобильное `expense_synced`.

**Граница roadmap:** CAT требует две разные действующие личности и три неотменённых расхода за 48 часов на одну поездку, включая mobile. Метрика по браузерам этого достоверно не доказывает. Нужна следующая отдельная задача: backend-authoritative факты, явный actor, непрозрачные корреляционные ID и объединение с mobile. В первом выпуске не отправлять raw event/user/expense IDs, PIN, токены, суммы, имена, описания и Error.message. Простое хеширование ID не принимать за полноценный privacy design.

## Интеграция и минимизация данных

Один `AnalyticsService` в `6-shared/analytics/analytics-service.ts`: типизированный `track`, очистка URL, загрузка SDK, согласие, навигация и отправка. Отдельно остаётся `analytics-event.ts` с контрактом событий. UI обращается к singleton `analyticsService`. Никакого универсального event bus и новой npm-зависимости. Вызовы аналитики не должны менять результат доменной операции.

Инициализация: production + валидный положительный counter ID + разрешённый hostname + явное согласие пользователя. До согласия не загружать сторонний script, не создавать аналитические идентификаторы и не буферизовать действия. Это выбранное продуктовое поведение, не заключение о требованиях законодательства. Отказ сохраняется; повторный выбор доступен в footer. Отзыв прекращает отправку и перезагружает страницу без SDK. Уже сохранённые cookies пользователь может очистить средствами браузера; автоматическое удаление cookies и исторических данных провайдера не реализовано.

Счётчик: `defer: true`; отключить Webvisor, clickmap, trackLinks, автоматические цели, ecommerce и accurateTrackBounce. Просмотры отправлять вручную через `hit` со статическим title и явным безопасным `referer`. Для `/event/<любое значение>` передавать `/event`, для неизвестного маршрута — `/other`; query/hash удалять, кроме разрешённых маркетинговых меток на первом просмотре. Не добавлять noscript pixel. Установить Referrer-Policy для исходящих запросов, исключающую path/query, и проверить в браузере. Не менять URL приглашения и процесс авторизации ради аналитики.

`defer` отключает автоматический просмотр, но сам по себе не доказывает безопасность остальных запросов SDK. Обязательный выпускной gate: проверить script/init/hit/reachGoal/params и фоновые запросы в браузере с тестовыми секретами в path/query/hash/referrer/title/формах. Если SDK отправляет исходный token-bearing URL вне управляемых полей, production включение блокируется до отдельного исправления. Не заявлять, что настройка hit автоматически очищает всё.

Очередь после согласия ограничена 50 сообщениями, TTL 30 секунд, только память вкладки; при блокировке загрузки очищается. Сначала init и первый hit, затем бизнес-события. Нет бесконечных retries или обещаний exactly-once доставки. Повтор эффекта React не должен дублировать просмотр одного navigation entry; обычный возврат назад считается новым просмотром.

## Источник входа

Сохранять разрешённый landing context только в памяти до решения об аналитике. Первый hit после согласия сохраняет исходный безопасный landing URL и внешний referrer origin; затем отправлять текущий маршрут, если он уже изменился. Не приписывать действия до согласия.

Внешние кампании: `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`; `utm_term` не собирать в первом выпуске. Источник и medium — известные коды; campaign/content — реестр публичных campaign codes. Неизвестные значения заменять `other`, не пропускать произвольный текст даже при ограниченной длине. Внешний referrer передавать только как origin; внутренний — нормализованный путь. Точность конкретного внешнего сайта ограничена этим решением.

Примеры управляемых ссылок: `/?utm_source=telegram&utm_medium=messenger&utm_campaign=travel_launch`; для скопированного приглашения `utm_source=commonex&utm_medium=referral&utm_campaign=trip_invite`. Последняя метка говорит «приглашение CommonEx», а не «Telegram»: clipboard не знает, где вставили ссылку. При копировании приглашения не наследовать рекламную кампанию организатора. Без меток и referrer часть посещений останется direct/unknown; не придумывать источник.

Метрика определяет метки по [первому просмотру визита](https://yandex.com/support/metrica/en/general/source-tags). В первом выпуске используем стандартную атрибуцию визитов провайдера; собственный persistent first-touch не вводим. Отказ от аналитики означает отсутствие данных, а не «прямой вход».

## Контракт событий v1

Общие параметры: `schema_version: 1`, `platform: web`. Только ограниченные enum-параметры. Имена ниже — JS goal IDs; все цели создаются в кабинете до включения.

| Событие | Точка отправки и значение |
| --- | --- |
| `trip_create_opened` | Открытие формы создания пользователем, не mount |
| `trip_created`, `trip_create_failed` | Один результат `EventService.createEvent`; reason только для failed |
| `invitation_requested` | Нажатие «скопировать ссылку», до запроса токена |
| `invitation_copied`, `invitation_failed` | Результат создания ссылки и успешного `copy`; false от copy — failure |
| `invitation_opened` | Первый показ token-bearing entry; без значения токена |
| `join_started`, `join_succeeded`, `join_failed` | Попытка `getEventInfo` и результат; `entry_method: token\|manual`. `succeeded` значит доступ получен, а не личность выбрана |
| `participant_claimed` | Успешный явный выбор себя; `entry_method: created\|token\|manual`; смена выбора — новое действие |
| `expense_opened` | Открытие формы добавления пользователем |
| `expense_submitted`, `expense_failed` | Сохранение обычной траты после retry; failed с reason |
| `settlement_viewed` | Фактическое открытие вкладки долгов; это текущий список долгов, не будущий guided settlement |
| `settlement_recorded`, `settlement_failed` | Итог создания возврата, отдельно от обычной траты |
| `store_link_clicked` | Явный click; `store: app_store\|rustore`; не считать установкой |

`reason: network | access_denied | not_found | validation | server | unknown`. Использовать существующий ApiError/status, не передавать message, response body и детали credentials. `entry_method` для выбора участника держать в памяти текущего входа; не выводить его из token после ручного/созданного входа. Тот же create/navigation не должен породить join success. Одна завершённая логическая операция — один результат, автоматические retries не дают новых событий.

## Отчёты и приёмка

1. Источники: source/medium/campaign → посещения → trip_created / join_succeeded / expense_submitted.
2. Организатор: home view → trip_create_opened → trip_created → participant_claimed → expense_submitted. invitation_requested/copied смотреть отдельной веткой, не требовать перед первой тратой.
3. Приглашённый: invitation_opened → join_started → join_succeeded → participant_claimed → expense_submitted; окно 48 часов. Ручной вход — отдельный сегмент.
4. Ввод: expense_opened → expense_submitted; failure reasons отдельным отчётом.

Это пользовательские web-воронки, шаги могут относиться к разным поездкам одного посетителя. Не называть их групповой активацией или CAT. До отдельного correlation design при нескольких поездках интерпретировать как поведение посетителя.

Сроки: не хранить сырые SDK-логи/exports в приложении; landing context — память текущей страницы, очередь — 30 секунд. Срок хранения у провайдера и удаление согласовать с доступными настройками/условиями счётчика до production включения и записать фактические значения в runbook. Не обещать управляемый TTL в Метрике без подтверждения.

Готовность: реализация возможна без доступа к кабинету с выключенным счётчиком; для production нужны ID отдельного web-счётчика, goals, проверенные настройки данных/хранения, обновлённые RU/EN policy и успешный сетевой privacy gate. Исследование не предполагает, что доступ к кабинету уже есть.

## Проверено при реализации 23–24 октября

Технический `nohit` запрос SDK с одним `defer: true` передавал исходный URL. Исправление задаёт очищенные `url`/`referrer` также при init и отключает Tag Manager. Параметры подтверждены исходным кодом текущего официального SDK и браузерной проверкой, но отсутствуют в публичной таблице init: сетевой regression gate обязателен перед включением. В полном тесте с вымышленным token-bearing URL не обнаружено чувствительных маркеров в 13 запросах. До согласия запросов аналитики нет. Подробности и ограничения — в [runbook](../../web/docs/analytics.md).

25 октября: по обратной связи объединены внутренние файлы в один сервис и файл контракта. Загрузка SDK остаётся после согласия; build-time ID уже встраивается в JS bundle. Для всех условных конструкций web включён ESLint `curly: all`.
