# Аналитика CommonEx Web: AppMetrica или Яндекс Метрика

Проверено 22 октября 2026 года по официальной документации. Это исследование провайдера и ограничения будущей интеграции; код и настройки внешнего счётчика не изменялись.

## Рекомендация

Для сайта подключить **Яндекс Метрику**, сохранив AppMetrica для Android. Официальный каталог SDK AppMetrica перечисляет Android, iOS, Unity, Flutter и React Native; браузерного SDK в каталоге нет. React Native не означает поддержку React/Next.js в браузере. Это вывод о пригодности опубликованных SDK, а не утверждение, что отправить web-событие в AppMetrica технически невозможно. [AppMetrica SDK](https://appmetrica.yandex.com/docs/en/sdk/platforms).

У AppMetrica есть Post API: события отправляются по HTTP с отдельным ключом; данные объединяются с SDK по `profile_id` или `appmetrica_device_id`, синхронизация выполняется каждые четыре часа. Это возможный будущий серверный канал, но не готовая замена web-счётчику, браузерным сессиям и источникам трафика. Не публиковать Post API key в браузерном bundle. [Post API](https://yandex.com/support/appmetrica-io/en/mobile-api/post/about).

## Воронки и удержание

Метрика поддерживает самостоятельный отчёт **«Воронки»**: шагами могут быть просмотры страниц, достижения JS-целей и параметры событий. Доступны конверсия относительно первого/предыдущего шага, группировки и ограниченное либо неограниченное окно прохождения; максимальное ограниченное окно — 360 дней. Это подходит для последовательности действий, растянутой на несколько визитов. Не нужно сводить задачу к составной цели одного визита. Создание отчёта требует прав владельца, представителя либо редактора. [Воронки](https://yandex.ru/support/metrica/ru/reports/funnels).

По актуальной документации в Метрике доступны также Retention, Rolling Retention, Retention Dynamics и когортный анализ, в том числе анализ качества источников и достижения целей. Сам факт повторного визита не равен продуктовому удержанию: критерий полезного повторного действия нужно определить отдельно. [Retention и Когорты](https://yandex.ru/support/metrica/ru/reports/retention-cohorts).

## Отправка событий в SPA

Официальная схема для SPA — `init` с `defer: true` и явный `hit` для первого просмотра и последующих значимых переходов. Это позволяет управлять URL и избежать двойного первого просмотра. События без смены страницы отправляются через `reachGoal`. [Настройка SPA](https://www.yandex.ru/support/metrica/ru/code/counter-spa-setup).

Разделение API:

| Метод | Назначение в CommonEx |
| --- | --- |
| `hit` | Просмотр безопасного канонического маршрута; `options.referer` и `options.title` задаются явно. |
| `reachGoal` | Подтверждённое продуктовое действие с устойчивым идентификатором цели. |
| `params` | Дополнительный контекст события или визита, пригодный для сегментации. |
| `userParams` | Характеристики посетителя, не контекст текущей поездки или источник очередного визита. |
| `setUserID` | Необязательная привязка внутреннего обезличенного ID к ClientID после появления устойчивой идентичности. |

Если не передать URL в `hit`, берётся `window.location.href`; если не передать заголовок, используется `document.title`. В `hit` имя опции реферера именно `referer`. [hit](https://yandex.ru/support/metrica/ru/objects/hit). `reachGoal` требует идентификатор созданной JS-цели. [reachGoal](https://yandex.ru/support/metrica/en/objects/reachgoal).

Важная настройка кабинета: если цель не создана отдельно или существует только внутри составной цели, параметры её `reachGoal` не попадут в отчёт «Параметры событий». Для продуктовых событий создавать отдельные JS-цели. Ограничения передачи: запрос до 8 КБ, до 512 параметров за визит, до 10 уровней вложенности; проекту достаточно плоского небольшого allowlist. [Передача событий](https://yandex.com/support/metrica/ru/data/visit-params-data).

Параметры посетителя описывают свойства вне конкретного времени посещения. Изменяемые признаки текущего визита следует передавать как параметры события/визита, а не как постоянные свойства пользователя. [Как работает Метрика](https://yandex.ru/support/metrica/ru/general/how-it-works).

## Источники входа

Метрика определяет источник по меткам и рефереру. **Метки должны присутствовать в первом просмотре визита**: если убрать их перед первым `hit`, последующий просмотр уже не восстановит правильную атрибуцию визита. Поэтому захватывать разрешённые метки до router/auth-редиректов и включать их в первый безопасный URL. [Определение источника](https://yandex.ru/support/metrica/ru/general/sources-tracking), [Обработка меток](https://yandex.ru/support/metrica/ru/general/source-tags).

Для внешних ссылок нужен единый словарь `utm_source`, `utm_medium`, `utm_campaign`, при необходимости `utm_content` и `utm_term`. Например, Telegram различается надёжнее через `utm_source=telegram&utm_medium=messenger`: реферер из мессенджера может отсутствовать. Метки регистрозависимы. `utm_referrer` поддерживается, но не следует принимать из него произвольный URL без очистки. [Обработка меток](https://yandex.ru/support/metrica/ru/general/source-tags).

Атрибуция маркетингового источника не заменяет продуктовый контекст: «из Telegram» и «вошёл по приглашению участника» — разные измерения. Предлагается передавать отдельный низкокардинальный `entry_point`/`entry_type`; конкретное название и набор значений согласовать с контрактом событий roadmap. Не размечать внутренние переходы маркетинговыми UTM: источник входа и последующие действия должны оставаться различимы.

## Защита URL и данных

Метрика прямо запрещает передавать идентифицирующие сведения через события, параметры, UTM, URL и заголовки, кроме специально предусмотренных функций. Значит, аналитике не нужны имена участников, email, тексты/суммы расходов, названия поездок, bearer/access/refresh-токены, invite credentials и полные URL с такими значениями. Это проектная минимизация данных на основе официальных ограничений. [Конфиденциальность](https://yandex.ru/support/metrica/ru/general/confidential-data).

Предлагаемый базовый режим: `defer: true`, `webvisor: false`, `clickmap: false`, `trackLinks: false`, `trackHash: false`, `sendTitle: false`; явные очищенные `hit` с нейтральным заголовком. `clickmap` и `trackLinks` по умолчанию включены, `sendTitle` тоже; одного отсутствия `webvisor` недостаточно. Официальный скрипт — `https://mc.yandex.ru/metrika/tag.js`. [Инициализация](https://www.yandex.ru/support/metrica/ru/code/counter-initialize).

Очищать не только query/hash, но и чувствительные сегменты path, предыдущий URL и заголовок. Для внешнего реферера обычно достаточно безопасного origin; для внутреннего — канонического маршрута. UTM разрешать отдельно, с ограничением длины/значений, а не копировать все параметры. **`defer` не является обещанием отсутствия любых сетевых данных/утечек:** нужно проверить реальные запросы SDK, включая события целей и технические запросы, на чувствительных маршрутах. Если SDK всё равно передаёт текущий raw URL, отложить его загрузку до удаления секрета из адресной строки или исключить такой экран из аналитики. Не утверждать безопасность только по unit-тестам адаптера.

## Границы идентичности и точности

`setUserID` связывает ID владельца сайта с ClientID только для посещений, в которых этот метод вызван. Документация метода не обещает автоматическую единую воронку с Android AppMetrica. [setUserID](https://yandex.ru/support/metrica/ru/objects/set-user-id).

Обычный посетитель определяется браузерными cookie; после их удаления считается новым. Кросс-девайс посетитель Метрики использует технологию Крипта. Это отдельный механизм, и его нельзя выдавать за точное объединение гостя, web-аккаунта и Android-профиля CommonEx. Для будущей общей воронки понадобятся общая семантика событий, явная идентичность/согласованные ID и отдельная проверка экспорта/объединения данных. [Глоссарий](https://yandex.ru/support/metrica/ru/general/glossary).

Блокировщики и сетевые ограничения могут не дать счётчику зарегистрировать цель; аналитика должна быть необязательной для работы интерфейса. Данные счётчика нельзя использовать как единственный источник истины для финансовых операций или точного количества совместных поездок. [Проверка целей и причины потерь](https://www.yandex.com/support/metrica/en/general/check-goal).

## Что проверить при реализации

1. Первый hit содержит разрешённые UTM и очищенный внешний referrer, отправляется один раз; SPA-переходы не дублируются.
2. Успешное действие отправляется после подтверждения операции; отмена/ошибка не выглядит успехом.
3. В реальных запросах отсутствуют invite/auth-токены, пользовательские названия, ID конкретных объектов и содержимое форм.
4. При отсутствии конфигурации, блокировке скрипта и ошибке сети сайт работает; локальная разработка и preview не загрязняют production-счётчик.
5. В кабинете созданы отдельные JS-цели, тестовая воронка строится в разрезе UTM и продуктового entry point. Внедрение без такой проверки ещё не подтверждает пригодность собранных данных.
