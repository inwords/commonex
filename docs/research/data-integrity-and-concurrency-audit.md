# Аудит backend: целостность данных и конкурентные операции

Дата: 2026-09-24. Область: PostgreSQL/TypeORM, HTTP/gRPC mutation paths и тесты `backend/`. Приоритеты ниже относятся к риску нарушения данных, а не к подтверждённой частоте инцидентов в production.

## Executive summary

Главный риск — идемпотентность не атомарна с изменением данных. Проверка ключа происходит до бизнес-операции, запись результата — после её транзакции. Два параллельных запроса с одним ключом способны оба создать event, users или expense; первичный ключ таблицы идемпотентности остановит лишь вторую запись результата, когда побочный эффект уже зафиксирован ([use case](../../backend/src/usecases/shared/idempotency.usecase.ts#L35), [схема](../../backend/migrations/default/1776518011496-init.ts#L8)).

Удаление события и создание расхода через V1/V2 сериализованы блокировкой одной строки event внутри транзакции: конкурентная операция получает конфликт `55P03`, а последующая видит `deletedAt`. Это реальная защита для этих маршрутов ([delete](../../backend/src/usecases/users/delete-event.usecase.ts#L31), [V2 expense](../../backend/src/usecases/users/v2/save-event-expense-v2.usecase.ts#L56), [repository](../../backend/src/frameworks/relational-data-service/postgres/repositories/event.repository.ts#L47)). Она не охватывает V1 добавление участников и создание share token: оба сначала читают event без блокировки, затем вставляют вне общей транзакции ([V1 users](../../backend/src/usecases/users/save-users-to-event.usecase.ts#L35), [token](../../backend/src/usecases/users/v2/create-event-share-token-v2.usecase.ts#L24)).

Схема задаёт первичные ключи, но не содержит внешних ключей на event/currency/user и не закрепляет бизнес-инвариант единственного активного share token. Проверка `schema-drift` покрывает совпадение TypeORM metadata с применёнными миграциями, но не достаточность этих бизнес-ограничений ([начальная миграция](../../backend/migrations/default/1750591686449-init.ts#L8), [share token migration](../../backend/migrations/default/1767464629981-init.ts#L8), [schema-drift test](../../backend/src/frameworks/relational-data-service/postgres/__tests__/schema-drift.spec.ts#L17)).

## Область и методика

Проверены цепочки контроллер → use case → repository → entity/миграция, а также DB-backed unit/e2e тесты. Статусы ниже означают: **защищено** — код и тест подтверждают механизм; **частично** — механизм есть, но не на всех путях; **риск** — найден конкретный достижимый сценарий. После статического аудита на предоставленной локальной PostgreSQL выполнен `schema-drift.spec.ts`: оба теста прошли, все миграции применены и TypeORM не видит pending schema changes. Конкурентные сценарии отдельно не воспроизводились. Индекс `.codegraph/` присутствует, но `codegraph` и `ast-index` в PATH/доступных инструментах отсутствуют; после попытки `codegraph explore` использован точечный поиск по репозиторию. Семантика транзакционного manager подтверждается [документацией TypeORM](https://typeorm.io/docs/transactions/), блокировок и deadlock — [документацией PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).

| Проверяемый пункт | Статус | Ключевой вывод |
|---|---|---|
| Идемпотентность | **Риск, P0** | Последовательный replay работает; конкурентное выполнение и сбой между commit и записью ключа не защищены. |
| Удаление event ↔ добавление expense | **Защищено** для V1/V2 expense; **частично** для иных мутаций | Общая блокировка event с `NOWAIT`; V1 users и share token её обходят. |
| Создание share token | **Риск, P1** | `find active → insert` без блокировки/уникального инварианта; возможны два активных токена и token после удаления event. |
| Повторные expense/refund | **Риск, P1** | Ключ необязателен, ID всегда новый; refund не связан с исходным expense. |
| Проверка affected rows | **Риск, P2** | `event.update` и `deleteByToken` не проверяют число затронутых строк. |
| Уникальность и внешние ключи | **Частично, P1** | PK есть; связи и бизнес-ограничения не закреплены в БД. |
| Rollback/deadlock | **Частично, P2** | Транзакционные записи откатываются при исключении; `NOWAIT` переводится в conflict; общего retry для deadlock/serialization failure нет. |
| Entities ↔ migrations | **Проверено динамически** | `schema-drift.spec.ts` подтвердил применённость миграций и отсутствие pending schema changes. |

## Подтверждённые находки

### P0 — повторный побочный эффект при конкурентном idempotency key

Сценарий: два запроса с одинаковым ключом одновременно читают отсутствие записи; оба выполняют `fn()`. Например, V2 expense внутри `fn()` фиксирует расход в собственной транзакции; после этого оба пытаются вставить один и тот же `idempotency_keys.key`. Один insert получает нарушение PK, но оба расхода уже созданы. Аналогичный разрыв существует при падении процесса после commit операции и до вставки ключа. Код: [lookup → fn → insert](../../backend/src/usecases/shared/idempotency.usecase.ts#L35), [V2 вызов и transaction](../../backend/src/usecases/users/v2/save-event-expense-v2.usecase.ts#L51), [PK](../../backend/migrations/default/1776518011496-init.ts#L8). Это вывод из порядка операций; конкурентный тест отсутствует. Существующие тесты проверяют только последовательный replay и mismatch ([V2 тест](../../backend/src/usecases/users/v2/__tests__/save-event-expense-v2.usecase.test.ts#L663), [HTTP e2e](../../backend/test/http/idempotency.e2e-spec.ts#L25)).

Дополнительно срок 24 часа задаётся value object, но `findByKey` не фильтрует `expiresAt`: до ежедневной очистки истёкший ключ продолжает replay и блокирует новое использование ([TTL](../../backend/src/domain/value-objects/idempotency-key.value-object.ts#L6), [lookup](../../backend/src/frameworks/relational-data-service/postgres/repositories/idempotency-key.repository.ts#L18), [cron](../../backend/src/api/cron/currency-rate-scheduler.controller.ts#L21)). Это P2, если контракт обещает пригодность ключа сразу после TTL; контракт TTL нужно зафиксировать отдельно.

### P1 — share token создаётся в гонке с другим token и удалением event

Сценарий A: два запроса одновременно не находят активный token и вставляют разные случайные значения. Уникален только `token`, а `event_id` имеет обычный индекс, поэтому оба остаются активными ([use case](../../backend/src/usecases/users/v2/create-event-share-token-v2.usecase.ts#L33), [entity](../../backend/src/frameworks/relational-data-service/postgres/entities/event-share-token.entity.ts#L5), [migration](../../backend/migrations/default/1767464629981-init.ts#L8)). Сценарий B: запрос проходит проверку ещё живого event, параллельный delete фиксирует `deletedAt`, затем первый вставляет token; создание успешно отвечает для уже удалённого event ([token flow](../../backend/src/usecases/users/v2/create-event-share-token-v2.usecase.ts#L24), [delete flow](../../backend/src/usecases/users/delete-event.usecase.ts#L31)). Использование такого токена дополнительно проверяет `deletedAt`, поэтому доступ к удалённому event не открывается ([read flow](../../backend/src/usecases/users/v2/get-event-info-v2.usecase.ts#L35)). Последовательные сценарии создания и reuse тестируются, конкурентные — нет ([share-token tests](../../backend/src/usecases/users/v2/__tests__/create-event-share-token-v2.usecase.test.ts#L54)).

### P1 — повторные расходы/возвраты и незакреплённые связи

`idempotency-key` в HTTP V2 опционален, а без него wrapper сразу вызывает бизнес-операцию. Каждый вызов генерирует новый ULID для expense; в expense есть только тип `expense`/`refund`, но нет ссылки на исходный расход или уникального client operation ID. Поэтому повторная отправка одинакового расхода или возврата создаёт новую денежную запись; даже при наличии ключа остаётся описанная выше конкурентная гонка ([controller](../../backend/src/api/http/user/user-v2.controller.ts#L95), [wrapper](../../backend/src/usecases/shared/idempotency.usecase.ts#L25), [ID](../../backend/src/domain/value-objects/expense.value-object.ts#L10), [модель](../../backend/src/domain/entities/expense.entity.ts#L1), [insert](../../backend/src/usecases/users/v2/save-event-expense-v2.usecase.ts#L92)). Это не утверждение, что два одинаковых expense всегда ошибочны: без стабильной идентичности операции backend не может различить дубликат и намеренный повтор.

Миграции не создают FK для `expense.event_id`, `expense.user_who_paid_id`, `user_info.event_id`, `event_share_token.event_id` или currency IDs; в entities это обычные `varchar`, а `split_information` — JSONB ([начальная миграция](../../backend/migrations/default/1750591686449-init.ts#L17), [token migration](../../backend/migrations/default/1767464629981-init.ts#L8), [expense entity](../../backend/src/frameworks/relational-data-service/postgres/entities/expense.entity.ts#L13)). V2 expense проверяет event/PIN, но не проверяет, что payer и split users существуют и принадлежат этому event; в ветке совпадающей валюты не делает отдельной проверки currency ID ([V2 flow](../../backend/src/usecases/users/v2/save-event-expense-v2.usecase.ts#L60), [ветка same currency](../../backend/src/usecases/users/v2/save-event-expense-v2.usecase.ts#L82)). Возможны ссылки на отсутствующих участников, а БД их не отклонит. Добавление FK требует предварительной оценки уже накопленных данных и soft-delete политики.

### P2 — результат UPDATE/DELETE теряет affected rows

`event.update` выполняет запрос и возвращает `undefined`, не проверяя `UpdateResult.affected`; `DeleteEventUseCase` после этого всегда формирует success. При необычном изменении строки между locked read и update либо при неверном transaction context возможен ответ об удалении без изменённой строки ([repository](../../backend/src/frameworks/relational-data-service/postgres/repositories/event.repository.ts#L93), [use case](../../backend/src/usecases/users/delete-event.usecase.ts#L47)). На штатном пути единый `ctx` и lock делают этот сценарий маловероятным. Аналогично `eventShareToken.deleteByToken` не сообщает, удалена ли строка ([repository](../../backend/src/frameworks/relational-data-service/postgres/repositories/event-share-token.repository.ts#L84)). Контекст типизирован как `unknown`; при значении не `EntityManager` repository молча переключается на глобальный DataSource, что снимает гарантию общей транзакции для ошибочного caller ([interface](../../backend/src/domain/abstracts/relational-data-service/types.ts#L1), [repository](../../backend/src/frameworks/relational-data-service/postgres/repositories/event.repository.ts#L98)).

### P2 — ограниченное покрытие rollback/deadlock и проблема down migration

Текущие mutation transactions используют переданный `ctx`; TypeORM требует именно transaction manager ([data service](../../backend/src/frameworks/relational-data-service/postgres/relational-data-service.ts#L29), [TypeORM](https://typeorm.io/docs/transactions/)). Тест доказывает rollback `event.update` при брошенном исключении; lock failures с `NOWAIT` и без него сохраняются как `QueryFailedError` ([rollback test](../../backend/src/frameworks/relational-data-service/postgres/repositories/__tests__/event.repository.spec.ts#L280), [NOWAIT test](../../backend/src/frameworks/relational-data-service/postgres/repositories/__tests__/event.repository.spec.ts#L108), [timeout test](../../backend/src/frameworks/relational-data-service/postgres/repositories/__tests__/event.repository.spec.ts#L158)). `55P03` теперь сознательно остаётся infrastructure error и доходит до transport catch-all; обоснование и аудит остальных SQLSTATE зафиксированы в [primary-source notes](postgresql-typeorm-expected-errors-primary-sources.md#local-runtime-audit-beyond-55p03). Обработки/retry кодов deadlock `40P01` и serialization failure `40001` в рассмотренных mutation paths нет; PostgreSQL прерывает одну из deadlocked transactions ([PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-DEADLOCKS)). Нельзя обещать автоматический retry без идемпотентного контура всей операции.

В `down` миграции idempotency index указан как `"public"."idx__idempotency_keys__expires_at"`, тогда как конфигурация поддерживает отличную от `public` схему. Для такой схемы откат может не найти индекс ([migration](../../backend/migrations/default/1776518011496-init.ts#L28), [config](../../backend/src/frameworks/relational-data-service/postgres/config.ts#L83)). Это статический риск rollback миграции, не проверенный на БД.

## Уже действующие защиты и границы проверки

- У V1/V2 expense и delete общий порядок: locked read event → проверка `deletedAt` → запись с тем же `ctx`; конфликт row lock не преобразуется в business error и возвращается как общий `INTERNAL_ERROR` ([V1 expense](../../backend/src/usecases/users/save-event-expense.usecase.ts#L54), [V2 expense](../../backend/src/usecases/users/v2/save-event-expense-v2.usecase.ts#L69), [delete](../../backend/src/usecases/users/delete-event.usecase.ts#L31), [repository](../../backend/src/frameworks/relational-data-service/postgres/repositories/event.repository.ts#L21)). PostgreSQL держит row lock до завершения транзакции ([документация](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)).
- V2 add-users использует тот же lock и transaction; V1 add-users — нет ([V2](../../backend/src/usecases/users/v2/save-users-to-event-v2.usecase.ts#L35), [V1](../../backend/src/usecases/users/save-users-to-event.usecase.ts#L35)). Создание event и начальных users атомарно в одной транзакции ([save event](../../backend/src/usecases/users/save-event.usecase.ts#L36)).
- После сохранённого успешного ключа последовательный повтор возвращает JSONB response, а другой hash получает ошибку; failed `Result` не кешируется ([idempotency use case](../../backend/src/usecases/shared/idempotency.usecase.ts#L38), [unit tests](../../backend/src/usecases/shared/__tests__/idempotency.usecase.test.ts#L103), [HTTP e2e](../../backend/test/http/idempotency.e2e-spec.ts#L46)).
- PK защищают IDs и сам token/key; дата currency rate тоже PK, а repository использует upsert ([миграции](../../backend/migrations/default/1750591686449-init.ts#L8), [key migration](../../backend/migrations/default/1776518011496-init.ts#L8), [rate upsert](../../backend/src/frameworks/relational-data-service/postgres/repositories/currency-rate.repository.ts#L96)).
- Entity metadata и миграции совпадают по семи таблицам (`currency`, `event`, `currency_rate`, `expense`, `user_info`, `event_share_token`, `idempotency_keys`), включая `deleted_at`, `is_custom_rate` и индексы token/key; набор entities перечислен в [index](../../backend/src/frameworks/relational-data-service/postgres/entities/index.ts#L9), миграции — [initial](../../backend/migrations/default/1750591686449-init.ts#L8), [rename](../../backend/migrations/default/1765728743776-RenameUserTable.ts#L4), [deleted_at](../../backend/migrations/default/1766314597487-init.ts#L6), [token](../../backend/migrations/default/1767464629981-init.ts#L6), [custom rate](../../backend/migrations/default/1771770993217-init.ts#L6), [keys](../../backend/migrations/default/1776518011496-init.ts#L6). На предоставленной локальной PostgreSQL [schema-drift test](../../backend/src/frameworks/relational-data-service/postgres/__tests__/schema-drift.spec.ts#L17) прошёл: миграции применены, pending schema changes отсутствуют.

## Пробелы тестирования

Нет DB-backed теста с двумя одновременно стартующими запросами на один idempotency key и явной проверкой числа side effects; существующие тесты выполняют первый и второй запрос последовательно ([e2e](../../backend/test/http/idempotency.e2e-spec.ts#L25), [V2 expense](../../backend/src/usecases/users/v2/__tests__/save-event-expense-v2.usecase.test.ts#L663)). Нет парного теста delete event ↔ insert expense/users/token с управляемым порядком блокировок; имеющийся repository test проверяет лишь два locked read ([event repository test](../../backend/src/frameworks/relational-data-service/postgres/repositories/__tests__/event.repository.spec.ts#L112)). Нет конкурентного теста двойного share token, теста отсутствующего payer/split user, повторного refund, проверки `affected=0`, deadlock/retry и `down` миграции в непубличной схеме. Это оценка рассмотренного набора тестов, а не заявление о production-инцидентах.

## Приоритизированные рекомендации

1. **P0:** определить контракт идемпотентности (обязательность ключа, время жизни, replay при одновременном запросе) и сделать резервирование ключа, бизнес-запись и результат одной атомарной операцией. Предусмотреть ответ/ожидание для второго in-flight запроса и тест с двумя соединениями. Не ограничиваться ловлей `23505` после commit побочного эффекта.
2. **P1:** выполнять создание share token под той же блокировкой event, что и delete, и явно закрепить инвариант токенов. Если нужен ровно один активный token, выбрать модель с заменой/версией или отдельной текущей строкой на event; индекс по условию `expires_at > now()` как partial unique constraint не подходит, поскольку PostgreSQL требует неизменяемое выражение индекса ([CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)).
3. **P1:** решить продуктовый контракт повторных expense/refund: требовать стабильный operation ID/ключ от клиентов для денежных мутаций; если refund должен ссылаться на исходный expense и иметь предел, добавить эту связь и проверку. Перед введением FK проверить существующие строки и политику soft-delete.
4. **P2:** возвращать/проверять affected rows для mutation repositories; отвергать некорректный transaction context вместо тихого fallback; добавить узкие тесты rollback и ошибки БД на границах транзакции.
5. **P2:** определить политику retry для `40P01`/`40001` только после атомарного idempotency-контура; сохранить `55P03` как явный конфликт либо описать клиентский retry. Проверить `down` миграции idempotency в непубличной схеме.
6. **Gate:** сохранить `schema-drift.spec.ts` обязательным CI-gate и добавить DB-backed конкурентные сценарии. Соответствие проверенной live schema и metadata подтверждено; атомарность перечисленных операций этим тестом не проверяется.
