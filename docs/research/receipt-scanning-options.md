# Исследование: распознавание чеков для заполнения траты

Проверено: 20.09.2026. Источники ниже — документация и репозитории самих поставщиков либо ФНС. Это техническое исследование, а не заключение о допустимости использования API.

Цель первой версии: **фото чека из любой страны с товарными позициями и ценами**. Внешний облачный API допустим. Поэтому полный список позиций важнее локального считывания QR. Ни один из перечисленных сервисов не гарантирует одинаковое качество для всех стран и языков без проверки на наборе чеков CommonEx.

Сравнение 1 000 чеков предполагает **один запрос/одну страницу на чек**, без повторных сканирований, хранения и инфраструктуры. Стоимость успешно распознанного чека будет выше, если фото приходится переснимать или отправлять повторно.

Широкий список языков базового OCR не означает поддержку разметки **описание ↔ количество ↔ цена**. Для решения нужен тест именно структурированных результатов по странам и форматам. Допустимый промежуточный вариант — многоязычный OCR плюс собственный парсер строк; при таком варианте поставщик отвечает за символы и координаты, CommonEx — за смысловые поля. [PaddleOCR: языки](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.en.md), [Azure: OCR](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/language-support/ocr?view=doc-intel-4.0.0).

## Отдельный случай: российский фискальный чек

QR-код содержит дату и время, сумму, признак расчета, номер фискального накопителя, номер фискального документа и фискальный признак. **Товарных строк в QR-коде нет**. Поэтому локальное считывание QR может надежно предложить сумму и дату, но для товаров нужно распознать напечатанный текст или получить электронный чек из внешнего источника. [ФНС: структура QR-кода](https://www.nalog.gov.ru/rn68/news/smi/9441211/).

ФНС публикует «Открытое API проверки чеков ККТ», но подключение требует заявки, регистрации и мастер-токена. Доступ предназначен для организации или ИП; пользователь должен дать согласие на доступ разработчика к информации о расчете. Условия ограничивают использование полученных данных выдачей электронного чека покупателю, проверкой и сообщением о нарушении (пп. 3, 5, 8–9). **Автоматическое составление/заполнение траты прямо не названо допустимой целью**; до выбора этой интеграции требуется подтверждение ФНС либо профильная правовая оценка. ФНС также может менять условия, лимиты и доступ. [ФНС: условия API](https://www.nalog.gov.ru/files/kkt/pdf/%D0%A3%D1%81%D0%BB%D0%BE%D0%B2%D0%B8%D1%8F%20%D0%B8%D1%81%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F.pdf).

## Практические схемы для сравнения

1. **Фото → облачное Receipt API → черновик.** Быстрый способ проверить ценность функции; схема уже содержит позиции и цены. Нужно оценить стоимость, поддержку стран, локаль валют, политику хранения и качество на своих чеках. Кандидат: [Mindee](https://docs.mindee.com/use-cases/extraction-models/receipt); варианты с ограниченным языковым покрытием: [AWS](https://docs.aws.amazon.com/textract/latest/dg/expensedocuments.html), [Google](https://docs.cloud.google.com/document-ai/docs/processors-list).
2. **Фото → собственный OCR-сервис → парсер → черновик.** Сохранять позиции, цены, итог и уверенность каждого поля; сверять суммы и показывать пользователю для подтверждения. Позволяет работать с чеками без QR и не зависит от облачного поставщика; потребует обработки изображений, парсера, измерения качества, сервера и политики хранения фото. Технические компоненты: [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) или [Tesseract](https://github.com/tesseract-ocr/tesseract).
3. **Локальный QR → черновик траты.** Считать QR на устройстве, заполнить сумму и дату, попросить пользователя ввести позиции вручную. Это полезный fallback для российских чеков, но **не соответствует требованию автоматических товарных позиций**. Основание: состав QR по [ФНС](https://www.nalog.gov.ru/rn68/news/smi/9441211/) и возможности [ZXing](https://github.com/zxing/zxing).
4. **QR → электронный чек через ФНС/ОФД.** Потенциально более структурированные позиции для России, но не охватывает другие страны, а право использовать API ФНС для создания трат не установлено. У ОФД следует отдельно проверять договор, доступность API и права на обработку данных; универсального открытого API ОФД в этом исследовании не подтверждено. [Условия ФНС](https://www.nalog.gov.ru/files/kkt/pdf/%D0%A3%D1%81%D0%BB%D0%BE%D0%B2%D0%B8%D1%8F%20%D0%B8%D1%81%D0%BF%D0%BE%D0%BB%D1%8C%D0%B7%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F.pdf).

[Tricount](https://tricount.com/expense-tracker-use-cases/restaurant-bills) |

Для CommonEx из этих примеров следует **вариант продуктового решения, а не доказанное универсальное правило**: после назначения позиций показать отдельные строки налога, чаевых, сервисного сбора и скидки. В качестве начального выбора можно распределять общие суммы пропорционально стоимости позиций каждого участника; пользователю дать возможность изменить их на равные доли и проверить итог до создания траты. Это соответствует подходу [Tab](https://play.google.com/store/apps/details?id=com.bring10.tab) и вариантам [Tab.team](https://www.tab.team/faq). Необъяснённую разницу между суммой позиций и итогом чека не следует автоматически считать чаевыми или налогом: [Tab.team](https://www.tab.team/faq) показывает такие расхождения на проверку. Официальные страницы выше не раскрывают точный алгоритм распределения последних копеек; его нужно определить и проверить отдельно в CommonEx.

## Что проверить экспериментом до выбора полного OCR

- Собрать согласованный набор чеков из целевых стран, языков, магазинов и условий съемки, включая длинные и выцветшие чеки; отдельно отметить чеки без QR и электронные чеки.
- Измерять точность суммы/даты, полноту товарных строк, совпадение суммы строк с итогом, задержку и долю черновиков, которые пользователи исправляют.
- Целевой поток CommonEx: распознать товарные строки, назначить каждую включённую позицию одному или нескольким участникам, разделить общие позиции поровну и передать рассчитанные доли в форму одной траты. Поэтому при сравнении сервисов измерять качество **товарных строк**, а не только общего итога и даты.
- Не считать демонстрационные метрики OCR/KIE на иных наборах доказательством качества на российских чеках.
