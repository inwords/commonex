# Изоляция backend для Android/KMM UI E2E в CI

Дата исследования: 2026-09-24. Основа: текущие файлы репозитория и первичная документация поставщиков. Варианты ниже — архитектурная оценка; время запуска и надёжность не измерялись, CI с новым окружением не запускался.

## Вывод

Для основного Android UI E2E job целесообразен **временный backend и PostgreSQL на том же GitHub runner**, поднимаемые Docker Compose на время job. Тестовый `autotest` APK должен получить адрес этого backend через конфигурацию сборки; данные, включая курс валют на текущую дату UTC, нужно готовить предсказуемо. Существующие backend HTTP/gRPC tests с отдельной БД и KMM network host tests остаются быстрыми нижними уровнями проверки. Короткая проверка удалённого backend после deploy может дополнять их, но не должна быть основным PR gate.

Причина выбора — текущий UI job уже выполняется на Ubuntu с эмулятором и Marathon, а repo уже содержит Docker-описание PostgreSQL и контейнер backend. Compose даёт изоляцию данных между job и запускает именно backend из проверяемого commit; это требует меньше новой orchestration-логики, чем Testcontainers. Временная БД сама по себе не устраняет общие зависимости: тесты должны создавать собственные события и не использовать фиксированные удалённые ID.

[GitHub runner docs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job). Отдельный удалённый `dev-api` может отличаться от backend-кода в PR; это следует из текущих workflow triggers и маршрутизации выше.

## Основные результаты аудита

| Приоритет | Риск | Почему это важно |
| --- | --- | --- |
| Критический | UI E2E пишет в общий удалённый backend. `commonex.ru/api` и `dev-api.commonex.ru/api` проксируются в один upstream `keepalive-nest-backend`. | Тестовые события попадают в тот же runtime/data plane, который обслуживает основной web API; очистка приложения и новый runner серверные данные не изолируют. |
| Высокий | Mobile и backend CI разделены path filters и не имеют зависимости друг от друга. | Android PR проверяется против уже развёрнутой версии, а backend PR вообще не запускает mobile E2E. Совместимость двух частей одного commit не является проверяемым инвариантом. |
| Высокий | При push в `main`, затрагивающем Android и backend, оба workflow могут идти одновременно. | UI suite может попасть на backend до, во время или после production deploy; результат нельзя однозначно связать с одним backend SHA. |
| Высокий | Серверное состояние общее, а один тест использует фиксированный event ID/PIN. | Параллельные job, ручное изменение или очистка remote event и Marathon retry могут давать недетерминированные результаты. |
| Средний | Тестовый APK нельзя перенаправить одной настройкой workflow: endpoint зашит в common code, модель не содержит port, `/api` снимает Nginx, cleartext запрещён. | Любой локальный контейнерный вариант требует небольшой явной точки конфигурации в `autotest`; иначе контейнеры будут подняты, но APK продолжит обращаться наружу. |
| Средний | Свежая БД не содержит курса валют на текущую UTC-дату, а внешний Open Exchange Rates зависит от сети, времени и ключа. | Даже корректно поднятый backend не готов к текущим currency/expense flows без детерминированного seed и блокировки внешнего scheduler-вызова. |
| Средний | При remote backend CI сохраняет только Android-отчёты, но не server/DB/proxy logs данного запуска. | Ошибку контракта, миграции или состояния трудно отличить от сетевого flake; локальный стек позволяет приложить все логи к тому же job. |

Вывод аудита: текущий job является полезным remote integration/smoke тестом, но слабым PR gate. Он проверяет реальную сеть и развёрнутую среду, однако не обеспечивает воспроизводимость, изоляцию данных и соответствие mobile/backend одному commit.

## Варианты

Оценки относительные для этого репозитория: «высокая» изоляция означает отдельное состояние на job; «верность» — насколько проверяется реальный backend, БД и wire path. Время запуска зависит от загрузки runner, cache образов, Gradle и эмулятора и должно быть измерено в пилоте.

| Вариант | Изоляция / параллельность | Верность backend | Время запуска | CI переносимость | Поддержка, секреты и отладка |
| --- | --- | --- | --- | --- | --- |
| Выделенный общий test backend + общая БД | Низкая без namespace/DB на job; параллельные PR и retry могут пересекаться | Высокая для развёрнутой версии, низкая для backend-кода конкретного PR | Быстро после deploy | Нужен доступ runner к внешней среде | Сервис, мониторинг, очистка данных, согласование версий и тестовые ключи; разбор отказа требует server logs и корреляции job ID |
| Docker Compose backend + Postgres на job | Высокая между jobs; внутри job тесты делят БД, поэтому данные создаются и очищаются по test ID | Высокая: настоящий NestJS, миграции, PostgreSQL и при proxy тот же `/api` path | Выше: сборка/загрузка образа, миграции и health wait | Хорошая на Linux runner с Docker; работает и локально | Compose manifest, seed и endpoint-конфигурация; можно сохранять compose logs и Android reports в artifact; внешние API нужно стабилизировать |
| Testcontainers на host runner | Высокая; динамические порты упрощают параллельные контейнеры | Высокая, если подняты сам backend и Postgres, а не только БД | Сопоставимо с Compose, зависит от pull/build | Требуется совместимый container runtime и host-side launcher | Дополнительный Node/JVM launcher, lifecycle/cleanup и передача адреса в APK; удобны runtime ports/logs. Не встраивать orchestration в Android instrumented test process |
| Локальный fake/mock HTTP server | Высокая, каждый job или test может иметь свои ответы | Низкая для server logic/DB, высокая только для UI и заданных HTTP сценариев | Обычно быстро | Хорошая; WireMock standalone может работать и в Docker, и как JAR | Нужно поддерживать сценарии и проверять, что они соответствуют API; не нужны backend secrets; удобно воспроизводить ошибки/задержки |
| Hybrid: real backend для критических UI flows + mock/contract tests для остальных | Высокая у локальных tiers, зависит от выбранного real-backend lane | Полное покрытие только у real-backend flows; contract tests проверяют форму взаимодействия | Быстрые tiers + один более долгий E2E lane | Зависит от реализации real-backend lane | Несколько уровней тестов и дисциплина контракта; легче локализовать поломку по уровню |

### Выделенный общий backend

Близок к нынешнему поведению: оставить `dev-api.commonex.ru` или завести отдельный test hostname. Это сокращает setup в UI job, но отдельный hostname сам по себе не изолирует состояние и не гарантирует соответствие commit. Для параллельной работы понадобятся как минимум отдельная БД/схема либо tenant на каждый job, выдача namespace, очистка после падений, стратегия deploy и фиксация версии backend. Иначе тест с удалением события и ретраи Marathon могут мешать другим запускам. Внешний test backend разумен как smoke после deploy, где требуется проверить сетевой маршрут, сертификат и конфигурацию среды, но не как единственный gate PR.

### Временный Compose stack

Рекомендуемая схема: `ui_tests_android` после checkout собирает backend-образ из данного SHA, поднимает Postgres и NestJS в отдельном Compose project (`-p` с уникальным run/job ID), ждёт health, применяет миграции (уже входят в backend Dockerfile), сеет курсы и данные тестов, затем запускает эмулятор и Marathon. `docker compose up --wait` ждёт состояния `running|healthy`; для порядка backend после Postgres нужен `depends_on: condition: service_healthy`, а для реальной готовности backend — его собственный healthcheck. [Docker Compose up](https://docs.docker.com/reference/cli/docker/compose/up/), [startup order](https://docs.docker.com/compose/how-tos/startup-order/). В `finally`/`if: always()` сохранять `docker compose logs` и отчёты, затем `down -v` для удаления тома БД; Docker подтверждает, что `-v` удаляет именованные тома проекта. [Docker Compose down](https://docs.docker.com/reference/cli/docker/compose/down/), [GitHub artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts).

На runner проброшенный порт доступен через `localhost`, а из Android emulator адрес host loopback — `10.0.2.2`; `127.0.0.1` внутри эмулятора указывает на сам эмулятор. [GitHub service-container networking](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idservices), [Android emulator networking](https://developer.android.com/studio/run/emulator-networking-address). Для приложения нужен variant-scoped endpoint с protocol/host/**port**; сетевой путь `/api` должен совпасть с нынешним Nginx (локальный proxy) либо `autotest` должен убрать этот префикс. Если используется HTTP, разрешение cleartext должно быть ограничено только `autotest` и адресом тестового сервера; release-конфигурация остаётся HTTPS. Android документирует per-domain cleartext rule и debug-only trust anchors, но последние зависят от `android:debuggable`. [Android Network Security Configuration](https://developer.android.com/privacy-and-security/security-config), [Android cleartext guidance](https://developer.android.com/privacy-and-security/risks/cleartext-communications).

Нельзя ограничиться проверкой `/health`: health проверяет БД, но не наличие курса на сегодняшний день. Seed должен быть идемпотентным и содержать все валюты, используемые UI flows; особенно нужно определить поведение на границе полуночи UTC. [`HealthCheckUseCase`](../../backend/src/usecases/health/health-check.usecase.ts), [`fixtures.ts`](../../backend/test/support/fixtures.ts). Не подменять внешним реальным Open Exchange Rates тестовые значения: ежедневный scheduler и внешний API создают зависимость от времени, сети и ключа. В тестовом runtime нужно отключить либо заменить плановое обращение к внешнему API, сохранив локальную логику backend; обязательный ключ задать бездействующим значением. Тестовый seed должен быть доступен лишь в CI setup, а не через публичный пользовательский endpoint.

### Testcontainers

Библиотека умеет поднимать/останавливать Docker-контейнеры в lifecycle **host-side** теста/скрипта и возвращает фактический host/mapped port. Это подтверждают официальные Node и Java guides. [Testcontainers Node usage](https://node.testcontainers.org/quickstart/usage/), [Testcontainers Java JUnit guide](https://java.testcontainers.org/quickstart/junit_5_quickstart/). В данном проекте orchestration должна жить в отдельном Node/JVM launcher на GitHub runner **до** установки APK и запуска Marathon: Android `BasicInstrumentedTest` выполняется на эмуляторе, тогда как Testcontainers требует доступ к container runtime хоста. Установка JUnit 4 `@Rule` непосредственно в instrumented test не даст ему Docker daemon и создаст lifecycle по тестам, плохо согласованный с Marathon retry/sharding. Это архитектурный вывод из текущего тестового пути и назначения Testcontainers. При нескольких эмуляторах launcher должен передать каждому адрес нужного backend; runtime mapped port нельзя захардкодить в уже собранном APK без поддержанной runtime-конфигурации. Сильная сторона Testcontainers — программируемые зависимости и динамические порты; цена здесь — дополнительная система orchestration при уже имеющемся Compose. Если позже backend tests перейдут на Testcontainers, повторно оценить общий launcher, но не связывать Android device tests с host-side JUnit extension.

### Mock/fake server и гибрид

WireMock официально поставляет standalone JAR и Docker image, которые можно запустить на runner и отдать эмулятору через `10.0.2.2`; его HTTP stubs позволяют воспроизводить ошибки, задержки и редкие ответы. [WireMock standalone](https://wiremock.org/docs/standalone/), [WireMock Docker](https://wiremock.org/docs/standalone/docker/). Подходит для UI состояний и network failure tests; не проверит NestJS, миграции, реальный расчёт долга и синхронизацию. Встраивание WireMock в само Android-устройство менее надёжно как исходная ставка: документация проекта прямо предупреждает, что старый Android guide может не относиться к новым версиям. [WireMock Android](https://wiremock.org/docs/solutions/android/). In-process HTTP fake внутри instrumented test возможен как отдельный вариант с MockWebServer, но потребует управлять запуском сервера и передачей его адреса приложению до создания `MainActivity`; Square описывает MockWebServer как средство базового HTTP-тестирования, а не полный API simulator. [OkHttp/MockWebServer](https://github.com/square/okhttp/blob/master/README.md#mockwebserver). Для CommonEx проще сначала использовать Ktor MockEngine в KMM host tests, где HTTP вызовы моделируются без сети; текущие [`EventsRemoteStoreImplTest.kt`](../../android/shared/feature/events/src/commonTest/kotlin/com/inwords/expenses/feature/events/data/network/store/EventsRemoteStoreImplTest.kt) уже применяют этот путь. [Ktor client testing](https://ktor.io/docs/client-testing.html).

Гибридный набор: (1) KMM client/mapper tests с mock transport для ошибок и краевых ответов; (2) backend HTTP/gRPC tests с Postgres; (3) небольшое число Android UI flows с временным настоящим backend; (4) при необходимости contract tests между мобильным consumer и backend provider. Pact определяет consumer-generated contracts и проверку их provider-версией; это помогает ловить несовместимость ответов, но не заменяет UI, синхронизацию, работу БД или сеть эмулятора. [Pact Broker overview](https://docs.pact.io/pact_broker/overview), [Pact provider verification](https://docs.pact.io/provider). Для начала достаточно расширить существующие client и backend tests; Pact/Broker стоит вводить лишь при подтверждённой потребности в независимых циклах выпуска и version matrix.

## Переход по этапам

1. **Сделать тесты самодостаточными.** Переписать `testJoinExistingEvent`, чтобы он создавал событие и получал ID/PIN в текущем job; проверить уникальность данных и cleanup для остальных flows. Зафиксировать минимальный UI smoke набор, который действительно требует реального backend, и собрать baseline времени/flake нынешнего job.
2. **Подготовить тестовую точку входа.** Ввести конфигурируемый endpoint только для `autotest` (protocol, host, port и правило `/api`), оставить deeplink host `commonex.ru` как пользовательский формат; проверить фактический Cronet request на API 36 эмуляторе. Выбрать локальный proxy для сохранения production path или явное снятие `/api` в тестовом варианте. Для HTTP добавить вариантное точечное network-security исключение; альтернатива — локальный HTTPS и тестовый CA.
3. **Поднять стек в UI job.** Создать отдельный Compose manifest backend + Postgres (+ proxy при выборе), собрать backend из checkout SHA, дать project name на job, readiness по health, seed курсов и тестовых данных, исключить плановый запрос к внешнему API. Изменить path filters так, чтобы значимые `backend/**`, `infra/**` и Android изменения запускали связанный UI E2E по одному commit; уменьшать набор только на основании времени и покрытия, а не через разные backend версии. Делать отдельную идентификацию результатов и тестовых данных; его сбой не должен скрываться retry локального E2E. Contract verification вводить отдельно, если интерфейс mobile/backend начнёт меняться независимо.

Критерии готовности пилота: APK обращается только к backend этого job; проход create → sync → join и чтение валют на свежей БД не требует внешнего ключа или фиксированного удалённого fixture; два параллельных job не делят БД/порты/тестовые ID; после падения доступны логи и результаты; teardown удаляет только ресурсы проекта данного job. Эти критерии следует подтвердить реальным CI прогоном — текущий документ устанавливает решение и проверяемый план, а не утверждает, что новый путь уже работает.
