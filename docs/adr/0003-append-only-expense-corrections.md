# Исправление трат через append-only версии

Пользователь исправляет трату, backend добавляет её полную новую версию, а клиент получает только последнюю. Старые версии остаются в БД. Механизм отмены убираем из клиентов; отмену, восстановление и компенсирующие записи в новую модель не вводим. Статус документа — **RFC**.

Совместимость определяется полем `event.version`: существующие события и создание без нового поля используют `1`, явное создание с `2` включает редактирование. Старые мобильные клиенты продолжают работать с событиями протокола 1, а для входа в события протокола 2 должны обновиться. Web доступен для обоих протоколов. Основная схема хранения трат — `id + version`, без компенсаций и legacy-адаптеров.

## Модель и пример

В существующую таблицу `expense` добавляется целочисленное поле `version`, начиная с 1. Идентификатор `id` обозначает одну логическую трату; первичный ключ становится составным `(id, version)` и обеспечивает уникальность этой пары вместо уникальности одного `id`.

| id  | version | description  | Доля участника |
| --- | ------- | ------------ | -------------- |
| abc | 1       | Ужин         | 100            |
| abc | 2       | Ужин         | 80             |
| abc | 3       | Ужин и такси | 120            |

Исправление копирует последнюю строку, меняет нужные поля и выполняет **INSERT** с `version + 1`. Старые строки не обновляются и не удаляются. Обычное чтение возвращает только максимальную версию каждого `id`: в примере — одну строку с долей 120. Долги рассчитываются только по этим строкам; складывать версии нельзя.

`createdAt` сохраняет дату траты, если пользователь явно её не исправляет; `updatedAt` новой строки — серверное время исправления. Событие и тип записи при исправлении не меняются. Возврат долга (`refund`) остаётся отдельной записью о передаче денег.

## Backend

- Создание сохраняет `version = 1`. Существующие ID трат сохраняются при миграции.
- Все поддерживаемые маршруты чтения трат выбирают максимальную версию по `id` внутри события и возвращают `version`. Индекс `(eventId, id, version DESC)` поддерживает этот запрос. Сохранять отдельное представление для старых клиентов не требуется.
- Новый запрос исправления передаёт ID траты, `expectedVersion`, полный исправленный payload, PIN события и заголовок `Idempotency-Key` для повторов.
- В транзакции сервер проверяет доступ и принадлежность участников событию, блокирует изменение, читает последнюю версию и сравнивает её с `expectedVersion`. Если она уже изменилась — `409`, без вставки. Иначе вставляет следующую версию. Для начала можно использовать существующую блокировку события.
- Для повторов используется существующий механизм `Idempotency-Key`; отдельных operationId/hash в Expense нет. В пределах TTL повтор возвращает прежний результат. После истечения TTL прежний `expectedVersion` приводит к конфликту; клиент перечитывает актуальное состояние, сохраняя черновик. Повтор не должен автоматически создавать следующую версию.
- Исправление только описания/плательщика сохраняет подтверждённые `exchangedAmount`. Изменение сумм, долей, валюты или даты требует расчёта автоматического курса на дату траты либо явно переданных custom amounts. Исторические версии не пересчитываются.

Составной ключ потребует обновить TypeORM mapping и проверить ссылки на `expense.id`: ссылка на конкретную версию должна включать `version`, а ссылка на логическую трату не должна требовать уникальности одного `id` в этой таблице.

## Клиенты и совместимость

На web и mobile в деталях траты появляется «Исправить» с заполненной текущими значениями формой. Действие отмены в mobile удаляется. Уже созданные старым механизмом отмены записи сохраняются как самостоятельные траты/возвраты: достоверной связи с оригиналом у них нет, автоматически объединять их нельзя.

Web после сохранения заменяет трату по `id` и пересчитывает долги. Mobile сохраняет `version` локально и при pull обновляет известную трату, если пришла большая версия, сохраняя её local ID. Меньшую версию игнорирует. Это обязательное изменение: [сейчас mobile pull](../../android/shared/feature/expenses/src/commonMain/kotlin/com/inwords/expenses/feature/expenses/domain/tasks/EventExpensesPullTask.kt) вставляет только неизвестные `serverId`.

Для offline-исправления mobile хранит отдельную ожидающую отправки команду с payload, expectedVersion и устойчивым Idempotency-Key. Pull не стирает её черновик. Если исходная трата ещё не создана на сервере, сначала подтверждается create, затем исправление; payload уже отправленного create нельзя менять под прежним ключом идемпотентности. При `409` клиент сохраняет черновик и показывает актуальную серверную трату, чтобы пользователь повторно подтвердил изменения.

Редактирование запрещено для событий протокола 1 на всех клиентах. Протокол нельзя повысить через публичные ручки. Backend отличает mobile по документированному User-Agent и определяет поддержку по номеру релиза: `CommonEx/11` и выше поддерживает версии событий 1 и 2, более ранние релизы — только 1. Дополнительный заголовок не нужен. Web и неизвестные клиенты не блокируются этой проверкой. Проверка подключена ко всем пользовательским HTTP/gRPC ручкам, включая прямые чтения трат, создание, участников и share tokens. Несовместимый mobile получает `CLIENT_UPDATE_REQUIRED` (HTTP 403, B4020), попытка редактирования старого события — B4021. Подробности: [сетевой контракт](../network-contracts.md#event-protocol-compatibility).

Текущий этап реализует только backend; mobile/web-код и показ диалога обновления остаются отдельной задачей.

Показ модалки на уже выпущенных версиях пока не подтверждён: он возможен только при наличии в них соответствующего механизма. Серверный отказ сам по себе не добавляет такой интерфейс. Перед запуском проверяется фактическое поведение старых сборок; если модалка невозможна, отказ может отображаться существующим экраном ошибки. Серверное ограничение также не может остановить офлайн-работу старого приложения с уже сохранённой базой.

## Переход и проверка

1. Миграция добавляет существующим строкам `version = 1`, заменяет ключ и обновляет все create/read пути. Проверяется, что исходные ID, суммы и даты сохранились.
2. Выпускаются backend с новым контрактом и клиенты с поддержкой версии. Существующие события сохраняют протокол 1; backend автоматически создаёт события версии 2 для mobile с User-Agent CommonEx/11 и выше; старые mobile создают версию 1, web передаёт версию явно. Глобальную минимальную версию приложения не вводим. Возможность модалки проверяется на старых сборках; старые пути доступа не должны обходить серверное ограничение.
3. Проверяются: выдача только последней версии; сохранность предыдущих; конкурентные исправления с `409`; повтор после timeout и истечения TTL; обновление известного ID на mobile; offline create → edit; курс и custom amounts; поддерживаемые HTTP/gRPC create/read; миграция локальной БД; отказ старым клиентам и сообщение об обновлении там, где оно реализуемо.

При откате отключается исправление, но чтение последних версий сохраняется. Возврат к старому backend, который выдаёт все строки, приведёт к двойному учёту и недопустим.

Основная цена решения — больше строк в БД и обновление мобильной синхронизации. Отдельный журнал событий, legacy-проекции и компенсации не требуются.
