# Извлечение черновика траты из фотографии чека

## Контекст и проблема

CommonEx делит траты внутри события между участниками. Сейчас [серверная трата](../../backend/src/domain/entities/expense.entity.ts) хранит описание, валюту, плательщика, дату и доли участников; отдельных товарных строк у неё нет. [Web-форма](../../web/src/4-features/Expense/ui/ExpenseForm.tsx) и [mobile-форма](../../android/shared/feature/expenses/src/commonMain/kotlin/com/inwords/expenses/feature/expenses/ui/add/AddExpensePaneUiModel.kt) принимают сумму и параметры разделения вручную. Mobile работает offline-first; создание траты доступно без сети, а синхронизация происходит позже ([доменная документация](../domain.md)).

Пользователь хочет сфотографировать чек **из любой страны** и получить распознанные **названия позиций и цены** для заполнения формы. Нужна работа с фотографией, а не только с QR-кодом. Внешний облачный API допустим, если ускорит запуск. Формулировка «любая страна» означает целевое покрытие, которое надо проверить на реальных чеках; ни один из изученных сервисов не доказал качество для всех стран и форматов.

Целевой сценарий: после распознавания пользователь назначает позиции участникам; затем открывается обычная форма **одной траты**, например «Ужин», с заранее рассчитанной суммой для каждого участника. Позиции служат входом для расчёта долей. Сохранять их как отдельные траты или менять серверную сущность Expense для первой версии не требуется. Это согласуется с существующим `splitInformation[]` в [контракте создания траты](../../backend/src/api/http/user/dto/create-expense.dto.ts), но требует отдельного экрана проверки чека и передачи рассчитанных долей в формы web и mobile.

OCR сам по себе возвращает текст, а фискальный QR российского чека содержит реквизиты для идентификации, дату и сумму, но не список покупок ([ФНС](https://www.nalog.gov.ru/html/sites/www.rn24.nalog.ru/nvkk/05-2023.pdf)). Кроме того, сервер поддерживает лишь EUR, USD, RUB, JPY, TRY и AED, а web сейчас не полностью поддерживает AED ([доменная документация](../domain.md)). Следовательно, полноценный сценарий «любая страна» может потребовать расширения валютной модели и интерфейса.

## Функциональные требования для первой версии

1. Пользователь делает фото чека или выбирает изображение и получает редактируемый черновик с названием и полной стоимостью каждой найденной позиции. При наличии в чеке также показываются количество, цена за единицу, итог чека, валюта, магазин и дата; отсутствие этих полей не блокирует ручное заполнение.
2. До сохранения пользователь может исправить, удалить или добавить позицию и назначить её одному или нескольким участникам. Общая позиция делится **поровну** между выбранными людьми. Ненужную позицию пользователь явно исключает из создаваемой траты; включённая позиция без назначенного участника блокирует переход к форме. Экран показывает рассчитанную сумму для каждого участника.
3. После подтверждения позиций открывается форма **одной** траты с редактируемым описанием (например, «Ужин»), итоговой суммой, валютой, плательщиком и предзаполненными индивидуальными долями. Итоговые доли должны совпадать с суммой создаваемой траты; пользователь может исправить их до сохранения. Распознавание никогда не создаёт трату автоматически.
4. Для позиции с указанной скидкой расчёт использует её конечную стоимость. Отдельную скидку на весь заказ, налог, чаевые и другие надбавки нужно распознавать как самостоятельные корректировки, а не как товары. Интерфейс показывает их и любую необъяснённую разницу между суммой позиций и итогом чека; разница не распределяется между людьми молча. Не подставляет неизвестную валюту по языку чека и не считает цену за единицу полной ценой строки.
5. Ошибка распознавания, плохое фото, неподдерживаемая валюта или отсутствие сети оставляют доступным обычное ручное создание траты. Сканирование не становится обязательным для offline-first mobile.
6. Один результат сканирования не должен порождать дубли при повторном запросе или повторном сохранении. Фото передаётся только для выбранного пользователем распознавания; срок хранения, журналы и условия провайдера должны быть определены до запуска.

Позиции чека в первой версии остаются **черновиком распределения**: сервер хранит одну трату и её доли, но не сохраняет принадлежность отдельных товаров. Если позже понадобится показывать состав чека или менять назначение позиций после создания траты, потребуется отдельное расширение доменной модели и API.

## Варианты

| Вариант | Плюсы | Минусы и ограничения |
| --- | --- | --- |
| **A. Облачный API с готовой моделью чеков**: [Azure Document Intelligence `prebuilt-receipt`](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/receipt?view=doc-intel-4.0.0), [Mindee Receipt](https://docs.mindee.com/use-cases/extraction-models/receipt), [Veryfi](https://docs.veryfi.com/). | Возвращает структурированные позиции, количества и цены; меньше собственной работы над извлечением. Azure публикует широкий [список языков для модели чеков](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/language-support/prebuilt?view=doc-intel-4.0.0), включая русский. Можно быстро сравнить качество на выборке CommonEx. | Платные запросы, отправка фото третьей стороне, ограничения регионов и условий обработки данных, зависимость от провайдера. Заявленное покрытие языка не гарантирует точность позиций на чеках каждой страны. Ключ API надо держать на сервере. |
| **B. Собственный сервис OCR + разбор строк**: [PaddleOCR](https://github.com/PaddlePaddle/PaddleOCR) с [моделью русского и других языков](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.en.md), либо [Tesseract](https://github.com/tesseract-ocr/tesseract) / [docTR](https://github.com/mindee/doctr); поверх них правила или локальная модель для связи названия, количества и цены. | Открытый код, контроль над фотографиями и инфраструктурой, возможность обучать или настраивать пайплайн под реальные чеки. Нет платы за каждый запрос внешнему API. | OCR не является парсером чека: нужны собственные нормализация, сопоставление строк и суммы, мультиязычные тестовые данные и эксплуатация отдельного сервиса. «Self-hosted» не означает автоматически низкую стоимость или высокую точность. Лицензии моделей и зависимостей проверяются перед внедрением. |
| **C. Локальное распознавание на устройстве**: OCR/QR в клиентах; для QR можно использовать [ZXing](https://github.com/zxing/zxing) или платформенные сканеры. | Фото не покидает устройство, возможно частичное использование без сети, мало нагрузки на backend. | Android, iOS и web потребуют разных реализаций либо тяжёлой общей обвязки. Получение **позиций и цен** из произвольного чека остаётся отдельной задачей парсинга. Российский QR сам по себе её не решает. [ML Kit Text Recognition v2](https://developers.google.com/ml-kit/vision/text-recognition/v2) перечисляет поддерживаемые наборы символов, поэтому его нельзя считать универсальным OCR для всех языков. |
| **D. Фискальный API по QR** (для российских чеков) | Теоретически позволяет получить или проверить официальный электронный чек без OCR, когда есть QR и разрешённый доступ. | Не покрывает фото без QR и чеки других стран. [Официальные технические условия ФНС](https://www.nalog.gov.ru/files/kkt/pdf/%D0%A2%D0%B5%D1%85%D0%BD%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%B8%D0%B5%20%D1%83%D1%81%D0%BB%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F.pdf) требуют заявки и мастер-токена; [условия использования](https://www.nalog.gov.ru/files/kkt/pdf/%D0%A3%D1%81%D0%BB%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F.pdf) ограничивают цели использования данных. Использование для автозаполнения расходов нельзя предполагать разрешённым без отдельной правовой проверки. |

Готовые self-hosted приложения для учёта чеков могут служить референсом, но не готовым компонентом: например, [Receipt Wrangler](https://github.com/Receipt-Wrangler) совмещает учёт с OCR/AI и интеграциями, а [Open Receipt OCR](https://github.com/iursevla/open-receipt-ocr) предлагает разные движки и очередь заданий. Их продуктовые модели и обязательные зависимости придётся оценивать отдельно; для CommonEx важнее заменить слой извлечения, чем встроить вторую систему учёта.

## Предлагаемое решение

Начать с **A как проверяемого кандидата**: построить черновик сканирования с внутренним форматом `receipt total / currency / date / merchant / items{name, quantity?, unitPrice?, totalPrice?, assignees, included} / source confidence`. После подтверждения вычислять из назначенных позиций `splitInformation[]` для одной траты и передавать результат в обычную форму, где пользователь может изменить описание, плательщика и суммы. Считать в минимальных единицах валюты: остаток от деления стоимости общей позиции распределять по одной минимальной единице в стабильном порядке участников. Например, 10,01 RUB на троих превращается в 3,34 + 3,34 + 3,33 RUB, а общая сумма остаётся 10,01 RUB. Вызывать провайдера через backend, чтобы ключ не попадал в web/mobile; обработчик изображений должен ограничивать размер и частоту запросов и не сохранять фото без продуктовой необходимости. Не привязывать доменную модель Expense к JSON конкретного API. На первом сравнении использовать Azure `prebuilt-receipt` и Mindee Receipt; оба документируют структурированные позиции и цены, а Azure явно перечисляет широкую языковую поддержку. Выбор конкретного провайдера отложить до испытания на чеках целевых стран.

Вариант **B** оставить технической альтернативой при недостаточном качестве, цене или неприемлемых условиях облака. Вариант **D** не включать в первую версию. QR можно позже использовать как дополнительную подсказку к дате и сумме, без зависимости основного сценария от ФНС.

## Проверка перед принятием и последствия

- Собрать обезличенный и разрешённый к использованию набор реальных фото разных языков, валют и типов чеков, включая длинные чеки, скидки, возвраты, размытые фото и чеки без позиций. Разделить выборку по странам, а не усреднять всё в одну метрику.
- Для каждого кандидата измерить точность названия и **полной стоимости строки**, пропуски и ложные позиции, совпадение суммы с чеком, задержку и стоимость одного успешного черновика. Порог приемлемости согласовать до выбора провайдера.
- Проверить сценарии общих и исключённых позиций, целочисленного распределения в минимальных единицах валюты и совпадения суммы долей с суммой траты. До реализации определить способ ручного распределения скидки, налога, чаевых и иной разницы между суммой строк и итогом чека.
- Для валют вне текущего набора требуется расширить поддержку либо явно показать ручной путь с поддерживаемой валютой; страна чека сама по себе не задаёт валюту.
- Проверить договорные условия, расположение обработки данных, срок хранения изображений провайдером и действующие правила обработки пользовательских фото до отправки реальных данных.

Статус остаётся **proposed**: схема «позиции → участники → одна трата с предзаполненными долями» и равное деление общих позиций определены, но конкретный провайдер и правило распределения общих корректировок ещё не утверждены.
